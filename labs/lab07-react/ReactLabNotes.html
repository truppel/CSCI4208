Lab 01: React

Interactive Story SPA

Requires: Node.js, npm, Chrome, a code editor, and the completed HTML Adventure Game

Download Starter Files: HTML Adventure Story starter files (ZIP)

This lab refactors the multi-file HTML Adventure Game into a React single-page application (SPA). The story, assets, choices, inventory, shop, combat, and win/lose paths stay the same. The architecture changes: instead of loading a new HTML document and copying inventory values into every URL, React renders page components and keeps one shared player state in memory.

Tooling Crash Course: Node.js, npm, and Vite

A React project uses browser code and development tools. The browser runs the finished application, while Node.js, npm, and Vite prepare and serve that application during development.

Tool or fileWhat it isHow this lab uses it
Node.js A program that runs JavaScript outside the browser. Runs npm and Vite on your computer. The story itself still runs in the browser.
npm The package manager installed with Node.js. Downloads React and Vite with npm install and runs named project commands such as npm run dev.
package.json The project manifest: its name, dependencies, and command scripts. Tells npm which tested package versions to install and tells students which development and build commands are available.
package-lock.json npm's exact dependency record, generated by npm install. Keeps installations reproducible. Commit or submit it, but do not edit it by hand.
node_modules/ The generated folder containing installed packages. Used locally by the tools. Do not edit or submit it; npm can recreate it from the package files.
Vite A development server and production build tool. Serves the app over http://localhost, follows module imports, converts JSX into browser-ready JavaScript, refreshes after saves, and creates the deployable dist/ folder.
vite.config.js A JavaScript module that customizes Vite. Enables Vite's React plugin so JSX and React development refreshes work. Most other settings can use Vite's defaults.

The commands have different jobs:

npm install       # Read package.json and install the tools and libraries
npm run dev       # Start Vite's development server while you work
npm run build     # Ask Vite to create a production-ready dist/ folder
npm run preview   # Locally serve the production build for a final check

Source files use ES modules: export makes a value available from one file, and import brings it into another. Vite starts at src/main.jsx, follows those imports, and builds the complete module graph. This is why file paths and extensions in imports must be correct.

React Crash Course: Components, JSX, and State

React is a JavaScript library for describing user interfaces as components. Instead of finding DOM elements and changing them manually, the application stores data and returns the UI that should exist for that data:

UI = a function of state

The react package supplies component and state APIs. The react-dom package connects those React components to the browser's DOM; its createRoot function mounts this app inside index.html.

ConceptWorking definitionExample in this game
Component A reusable JavaScript function whose capitalized name returns part of the interface. Home, Inventory, and GamePage are components. JSX renders them as <Home /> or <Inventory />.
JSX HTML-like syntax written inside JavaScript. Vite transforms it before the browser runs it. <p>Gold: {player.gp}</p> combines an element with a JavaScript expression. JSX uses forms such as className, htmlFor, and onClick.
Props Read-only inputs passed from a parent component to a child. <GamePage title="Forest"> passes a title prop. Props let one reusable component render different content.
Children The JSX nested between a component's opening and closing tags. Forest's image, story, and choices become the children rendered inside GamePage.
State Data React remembers between renders. Calling its setter requests another render. The current page, player inventory, door state, goblin health, and form text are state.
Hook A function whose name begins with use and connects a component to a React feature. Hooks are called at the top level of components or other Hooks, not inside conditions or event handlers. useState adds local state, useContext reads shared state, and useGame is this app's custom Hook.
Context A way for a provider to share values with components below it without passing the same props through every level. GameProvider owns the current page and player; useGame() lets pages and inventory read or update them.
Event handler A function React runs after a browser event. onClick={attack} runs combat, and onSubmit={submit} handles the Dungeon form without loading a new document.
Conditional rendering Using JavaScript conditions to choose which JSX exists. Swamp chooses between its normal scene and DeathScreen; Goblin chooses combat, victory, or game-over controls.

A typical interaction follows one predictable cycle:

User clicks a control
        ↓
React runs its event handler
        ↓
The handler calls a state or Context update
        ↓
React runs affected components again
        ↓
React updates only the DOM needed to match the returned JSX

Local state versus shared state: keep a value in the smallest component that needs it. Swamp's death choice and Dungeon's typed word are local because no other scene uses them. Gold, health, keys, and the current page are shared through Context because many scenes need them. Later goals make this distinction concrete one feature at a time.

Motivation

The HTML version treats every scene as a separate document. Moving to another scene loads another file and starts another JavaScript environment. Because those documents cannot directly share variables, the game places gp, hp, ap, and keys into URL query parameters and copies those parameters into every link and inventory iframe.

React lets the application remain in one document. Each scene becomes a component, and changing scenes means asking React to render a different component. Player data can live above every scene in a shared provider, so it no longer needs to travel through the URL.

Goal

Refactor the existing interactive story into a React SPA while keeping feature and visual parity with the HTML version.

Work iteratively: Keep npm run dev running. At the end of every goal, stop coding and complete its Assess phase before continuing. Each page is imported and registered in the same goal that creates it, so the application remains runnable throughout the lab.

Approach — Design Phase

Goal 2: Render the Home Component with JSX

Approach — Design Phase

A React component is a JavaScript function that returns UI. JSX looks like HTML inside JavaScript. Component names begin with capital letters so React can distinguish them from HTML elements.

Design: Separate startup from page rendering. main.jsx mounts React once, App.jsx selects the visible page, and Home becomes the first component in a registry later goals will extend. React derives the visible DOM from component return values rather than from permanent markup in index.html.

Goal 3: Create SPA Page Navigation

Approach — Design Phase

The HTML app navigates by assigning a file to an anchor's href. The SPA stores the current page name in state and looks that name up in the pages registry created in Goal 2. State is a value React remembers between renders. Calling its setter selects another registered component.

Design: Represent navigation as data. A page-name string is state, the registry maps that string to a component, and event handlers update it. React then re-renders App and selects the new scene without requesting another HTML document. This goal keeps the state local temporarily so the pattern is visible before Context centralizes it.

Apply — Implementation Phase

How these steps extend the app: Step 1 creates the first destination component, Step 2 makes that destination selectable, and Step 3 connects Home's Start event to the page-state setter. Together they produce the first working SPA transition.

Goal 4: Share Inventory with Context

Approach — Design Phase

Passing goTo and player data through every page as props would become repetitive. Context allows a provider near the top of the component tree to share values with any component beneath it.

Design: Make GameProvider the owner of cross-scene state: the current page and player inventory. It exposes focused actions—goTo, updatePlayer, startGame, and acceptQuest—so consumers request changes instead of mutating data. Provider updates re-render components that read the changed Context value.

The HTML inventory query string:

?gp=0&hp=3&ap=1&keys=0

becomes one JavaScript object:

{ gp: 0, hp: 3, ap: 1, keys: 0 }

The player begins with zero gold. Accepting the elder's quest in Intro adds the promised 5-gold deposit before the app renders Overworld.

Apply — Implementation Phase

How these steps extend the app: Step 1 creates the shared state owner and game actions; Step 2 places that provider above the app; Step 3 creates a Context consumer for inventory; Step 4 moves App and Home from temporary props/local state to Context; and Step 5 connects the Intro story action to the shared gold update.

Step 1: Create src/GameContext.jsx.

CREATE FILE — use the complete listing
import { createContext, useContext, useState } from 'react'

const startingPlayer = { gp: 0, hp: 3, ap: 1, keys: 0 }
const GameContext = createContext()

export function GameProvider({ children }) {
  const [page, setPage] = useState('home')
  const [player, setPlayer] = useState(startingPlayer)

  function goTo(nextPage) {
    setPage(nextPage)
  }

  function updatePlayer(changes) {
    setPlayer((current) => ({ ...current, ...changes }))
  }

  function startGame() {
    setPlayer(startingPlayer)
    setPage('intro')
  }

  function acceptQuest() {
    setPlayer((current) => ({ ...current, gp: current.gp + 5 }))
  }

  return (
    <GameContext.Provider value={{ page, player, goTo, updatePlayer, startGame, acceptQuest }}>
      {children}
    </GameContext.Provider>
  )
}

export function useGame() {
  return useContext(GameContext)
}

createContext defines the shared channel, GameProvider owns its state, and useGame is a custom Hook that gives consumers one consistent way to read the nearest provider. The two useState calls are independent: page changes select UI, while player changes preserve inventory across those page selections.

The spread syntax { ...current, ...changes } copies the current player and overwrites only the fields supplied in changes. React state should be replaced, not mutated directly.

Goal 5: Reuse Components and Props

import { useGame } from '../GameContext.jsx'

export default function ActionLink({ to, children, beforeNavigate }) {
  const { goTo } = useGame()

  function navigate(event) {
    event.preventDefault()
    beforeNavigate?.()
    goTo(to)
  }

  return <a href={`#${to}`} onClick={navigate}>{children}</a>
}

The anchor remains recognizable and accessible. import { useState } from 'react'
import { useGame } from '../GameContext.jsx'
import GamePage from '../components/GamePage.jsx'
import ActionLink from '../components/ActionLink.jsx'

export default function Hut() {
  const { player, updatePlayer, goTo } = useGame()
  const [open, setOpen] = useState(false)
  const [message, setMessage] = useState('')

  function useDoor() {
    if (open) {
      goTo('hut-inside')

      updatePlayer({ keys: player.keys - 1 })
      setOpen(true)
      setMessage('The door unlocked, but the key broke apart.')
    } else {
      setMessage('The door is locked.')
    }
  }

  return (
    <GamePage title="Witch's Hut">
      <button className="image-button" onClick={useDoor}>
        <img
          src={open ? '/assets/Open-Door.gif' : '/assets/Locked-Door.gif'}
          width="240"
          alt={open ? 'Open door' : 'Locked door'}
        />
      </button>
      <p>{message}</p>
      <ActionLink to="swamp">Exit</ActionLink>
    </GamePage>
  )
}

The ternary operator condition ? valueWhenTrue : valueWhenFalse selects the door image and its alternative text. Updating three state values causes React to render the new image, message, and inventory.

Create src/pages/Goblin.jsx. The player's HP and gold are shared state; the goblin's HP and battle message are local state.

CREATE FILE — use the complete listing
import { useState } from 'react'
import { useGame } from '../GameContext.jsx'
import GamePage from '../components/GamePage.jsx'
import ActionLink from '../components/ActionLink.jsx'

export default function Goblin() {
  const { player, updatePlayer } = useGame()
  const [goblinHP, setGoblinHP] = useState(3)
  const [message, setMessage] = useState("Goblin ambush! You're threatened by a goblin!")

  const won = goblinHP <= 0
  const dead = player.hp <= 0

  function attack() {
    const nextGoblinHP = goblinHP - player.ap
    setGoblinHP(nextGoblinHP)

    if (nextGoblinHP <= 0) {
      updatePlayer({ gp: player.gp + 3 })
      setMessage('You defeated the goblin and find 3 gold!')
      return
    }

    const nextHP = player.hp - 2
    updatePlayer({ hp: nextHP })

    if (nextHP <= 0) {
      setMessage('You Died.')
      return
    }

    setMessage(`You hit for ${player.ap} damage, it has ${nextGoblinHP} HP left. You take 2 damage.`)
  }

  return (
    <GamePage title="Hills">
      <img src={won ? '/assets/treasure.gif' : '/assets/goblin.gif'} width="480" alt={won ? 'Treasure' : 'Goblin'} />
      <p>{message}</p>
      {dead ? (
        <ActionLink to="home">Game Over</ActionLink>
      ) : won ? (
        <ActionLink to="forest">Go back</ActionLink>
      ) : (
        <><button onClick={attack}>Fight</button> <ActionLink to="forest">Retreat</ActionLink></>
      )}
    </GamePage>
  )
}

The player attacks first. If that attack defeats the goblin, the function awards gold and returns before the goblin can retaliate. This matches the combat progression described by the original HTML lab and makes repeated battles useful for earning gold. The nested ternary renders one of three sets of controls: game over, victory, or combat.

Concluding Notes

The original and refactored games produce nearly the same experience, but their data flow is different. The multi-page version makes the browser responsible for document navigation and manually serializes state into URLs. The React version keeps the application mounted, represents scenes as components, and lets state determine what React renders.

React's central idea is:

UI = a function of state

Instead of finding an element and changing it, update state and describe the UI that should exist for that state.

Appendix: State Placement Guide

Ask, “Which components need this value?”

Value Placement Reason
Current scene Shared Context state Navigation affects the entire app
Gold, health, attack, keys Shared Context state Many scenes read or update them
Dungeon input text Local Dungeon state No other scene needs the typed value
Goblin HP Local Goblin state It belongs to one encounter
Hut door open/message Local Hut state It only controls the Hut UI
Swamp death choice Local Swamp state It only selects the Swamp result
